# QY-DASH 版本号管理与发版规范 (Versioning Specification)

本文档明确定义了 **QY-DASH** 项目的语义化版本号（Semantic Versioning）管理规范与自动化流水线触发机制。所有维护者与 AI 编码助手在发版时必须严格遵守本规范。

---

## 📌 版本号格式定义

项目统一遵循 `v<Major>.<Minor>.<Patch>` 格式（例如：`v2.0.1`）：

```text
       v  2  .  0  .  1
          │     │     │
          │     │     └── [Patch]  修订版本号：日常变更、功能迭代、Bug修复 (默认只变此位)
          │     └──────── [Minor]  次版本号：跨模块大规模深度重构 (无大规模重构严禁增加)
          └────────────── [Major]  主版本号：重大代际架构演进 (用户未明确要求严禁增加)
```

---

## 🚨 核心版本号演进三大红线规则

### 1. 🔒 第一位版本号 (Major: `X.0.0`)
- **严格红线**：**用户未明确提出要求，绝对不得增加第一位版本号！**
- **适用场景**：
  - 必须由用户亲自提出并明确要求升级主版本。
  - 伴随系统出现彻底代际更迭、不向下兼容的颠覆性重写（例如从最初的本地单机版升级至现在的全新分布式 C/S 架构 `v2.0.0`）。
- **约束要求**：AI 助手与协作者严禁自行评估并递增第一位版本号。

### 2. ⚠️ 第二位版本号 (Minor: `x.Y.0`)
- **严格红线**：**无大规模重构，绝对不得增加第二位版本号！**
- **适用场景**：
  - 发生了跨系统模块的全面重构、核心通信链路层协议重大演进或底层核心数据存储架构重写。
  - 必须在发版说明中明确向用户说明涉及的具体“大规模重构范畴”并达成共识后方可递增。
- **约束要求**：常规新功能追加、局部接口调整、扩展模块开发均不得递增第二位版本号。

### 3. ⚡ 第三位版本号 (Patch: `x.y.Z`)
- **默认规则**：**默认一律且仅变更第三位版本号！**
- **适用场景**：
  - **日常特性迭代**（例如：新增 Cloudflare Token 有效性验证、添加新探针指标、Xray 节点配置参数扩展等）。
  - **缺陷与故障修复**（例如：修复离线状态心跳脱节、修复密钥重置、修复样式显示等）。
  - **视觉体验优化**（例如：去除 AI Slop 痕迹、响应式适配、布局优化等）。
  - **性能与构建调优**（例如：加速编译管线、减少镜像体积等）。
- **演进范例**：`v2.0.0` ➔ `v2.0.1` ➔ `v2.0.2` ➔ `v2.0.3` ...

## 🚀 流水线构建与发版触发规则 (CI/CD Rules)

为了避免日常代码提交产生大量冗余的 Docker 镜像构建，GitHub Actions (`.github/workflows/docker.yml`) 已配置严格的发布触发策略：

| 触发源 | 是否触发打包部署 | 说明 |
| :--- | :---: | :--- |
| **`main` 分支日常代码推送** | ❌ **不触发** | 日常功能研发、测试及普通提交均不触发打包流水线 |
| **`v*` Release Tag 推送** | ✅ **触发构建与部署** | 仅在推送符合规范的 Tag 时（如 `v2.0.1`）触发编译、镜像打包与 VPS 部署 |
| **`workflow_dispatch` 手动触发** | ✅ **按需触发** | 支持在 GitHub Actions 页面进行紧急手动构建与调试 |

## 🎯 单一真实源 (Single Source of Truth) 机制

从 `v2.0.3` 起，项目全面消除所有文件中的版本号硬编码，确立 **`web/package.json`** 为全项目的唯一版本真实源：

1. **前端 React 全栈**：
   - 统一由 `web/src/version.ts` 从 `package.json` 导出 `APP_VERSION` 常量。
   - 所有 UI 组件（页眉徽章、页脚、节点卡片、节点表格、抽屉详情）均引用 `APP_VERSION`，严禁硬编码字面量。
2. **服务端 Go 守护核心 (`qy-core`)**：
   - `web/web.go` 原生内嵌 `package.json` 并提供 `web.Version()` 方法。
   - 若未通过 `-ldflags` 传参，服务端与各接口默认自动解析内嵌的 `package.json`，开发调试无需编译参数。
3. **构建与 CI 流水线 (`Makefile` & GitHub Actions)**：
   - `Makefile` 动态执行 `node -p "require('./web/package.json').version"`（降级 grep/awk）提取版本号并注入 `-ldflags`。
   - `.github/workflows/docker.yml` 与 `scripts/release.sh` 自动读取并同步更新 `web/package.json`。
4. **日常发版极简维护**：
   - **日常发版只需修改 `web/package.json` 中的 `version` 字段，全系统（前端、后端、探针、打包脚本、CI/CD）全自动无感同步**。

## 🛠️ 标准发版操作流程

当完成一个功能迭代或修复批次准备发版时，遵循以下标准流程：

```bash
# 1. 暂存并提交代码至 main 分支 (此操作不会触发 CI 打包)
git add .
git commit -m "feat: 增加验证 Cloudflare Token 有效性功能"
git push origin main

# 2. 依据本规范默认递增第三位版本号创建 Release Tag
#    当前为 v2.0.0 -> 下一版本为 v2.0.1
git tag -a v2.0.1 -m "Release v2.0.1: 增加 Cloudflare Token 校验与托管域名探测功能"

# 3. 推送 Release Tag 至远程仓库 (触发 GitHub Actions 编译、镜像构建与 VPS 部署)
git push origin v2.0.1

# 4. 实时监控 GitHub Actions 构建流程，确保打包通过
gh run watch $(gh run list --workflow="docker.yml" --limit 1 --json databaseId -q '.[0].databaseId')
```

## 🤖 AI 助手行为准则

当用户发出“发布版本”、“发版”、“打 tag 推送”等指令时，AI 助手必须：
1. **优先检查当前最新的 Git Tag**。
2. **默认只递增第三位版本号（Patch: `x.y.Z`）**。
3. **除非用户显式要求升级第一位，或者本次提交确实涉及跨模块重大架构重写并向用户明确说明升级第二位，否则坚决只递增第三位**。
4. **确保本地构建、测试和代码提交完成且工作区干净后，再创建 Tag 并推送**。
5. **每次发版后必须使用 `gh` 命令实时监控 GitHub Actions 打包过程**：推送 Release Tag 后，必须立即执行 `gh run watch` 监控编译与部署流程，直至流水线状态为 `completed / success`；若流水线报错失败，必须立即拉取失败日志定位根因并修复，坚决避免发版失败悬空。
